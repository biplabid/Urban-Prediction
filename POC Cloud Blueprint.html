Overview — three planes, one always-on

Classification and simulation run in batches you trigger by hand. Only the serving plane is "live," and it's fully static — no server executes code when a browser asks for a tile.

Overview — the reference stack, wearing proper IAM

Since Earth Engine already lives on Google Cloud, this variant keeps it but swaps the free-tier shortcuts (manual Colab runs, public-read objects) for the services a reviewer would expect in a GCP solution architecture: scheduled triggers, a managed notebook, Secret Manager, and an explicit CDN + load balancer.

Honest trade-off: the forwarding rule behind this load balancer carries a small fixed hourly charge (~$18/month) regardless of traffic. For 10 DAU, Firebase Hosting or a Cloud Storage bucket behind Cloud CDN without the LB is cheaper — use this pattern only if the exercise specifically wants the enterprise-shaped GCP answer.

Recommendation for a solo POC

Build on the reference stack: Earth Engine's free CART classifier and managed catalog remove the heaviest lift (imagery ingestion + classification), and a static PMTiles-on-CDN serving layer means there is nothing running that can incur a surprise bill. Treat the AWS and GCP columns as the "how would this look as a resume-grade solution architecture" answer — worth having ready, not worth deploying twice for a phase-1 demo.

Reference: Abdelsamie et al., "Current and Potential LULC Scenarios in Dry Lands Using a CA-Markov Simulation Model and CART Method: A Cloud-Based Google Earth Engine Approach," Sustainability 2024, 16, 11130 — the CART + CA-Markov methodology this pipeline mirrors, applied here to Guwahati instead of Qena.
